# 使用说明

工具只做三件事：驱动 APP 升级、判定结果、留下日志和截图。它不修改 PHP 后台的升级配置。

## 启动前

1. 在 PHP 后台按策略配好升级包。
   - S1：ufw 内部版本保持 2.0.0，后台版本名改成更高的号，例如 2.0.1。
   - S2：若后台能按设备当前版本同时匹配两条包，工具可无人值守交替；若同一机型只允许一条生效配置，把 `config/global.yaml` 的 `s2_model` 改为 `single`，工具会在方向不符时暂停，等人切完后台再点「继续」。
2. 手机只连接一台，打开 USB 调试并授权这台电脑。`adb devices` 里应只有一台状态为 `device`。
3. APP 已安装并完成首次登录。登录不是用例的一部分。
4. APP 改版后按《元素校准》核对 yaml 里的包名和页面元素。包名若被改回 `com.example.*`，实机任务会被拒绝；`--dry-run` 不受这个限制。

## 启动

```bat
python start.py
```

浏览器打开 `http://127.0.0.1:8765/`。没有真机时：

```bat
python start.py --dry-run
```

dry-run 用假设备走完调度、判定和报告，不会调用 adb。

页面上可以改轮次和超时，这些修改只对这一次任务有效，不会写回 `config/`。

## 怎么跑

1. 选择眼镜、戒指或手表。
2. 勾选场景。T02 是 S1，T03 是 S2，两者不能放在同一次任务。
3. 填写每场景轮次。T02 或 T03 设成 200，就是长稳压测。
4. 点开始。一台手机跑完后点停止，拔线，换下一台，点「刷新设备」，再新建任务。
5. 报告在 `output/reports/<链路_策略_时间戳>/`，同时有 `report.csv`、`report.html`、`result.json`。

场景按勾选顺序串行，每个场景连续跑满轮次再换下一个。死机后，同任务剩下的场景记 SKIP，不再执行。

## 结果码

| 结果 | 含义 |
| --- | --- |
| PASS | 升级成功，需要重连时也重连成功 |
| FAIL_UPGRADE | 升级或版本校验失败，设备仍可连接 |
| HUNG_DEVICE | 断开后超过重连超时，且连续确认仍未连接 |
| SKIP | 这一轮没能有效执行，或因为前序死机被跳过 |
| ABORT_ENV | 手机掉线、蓝牙关闭、未登录、电量过低、后台没配可升级的包 |
| STALE_POLICY | 后台策略和预期不符，任务停止 |

`ABORT_ENV` 会立刻终止整个任务，同一任务剩下的场景记 SKIP，不会继续跑成一串假失败。

矩阵单元格只保留 PASS、FAIL、HUNG、SKIP。同一列有死机记 HUNG，有升级失败记 FAIL，全部 PASS 才记 PASS。

## 升级要跑多久，怎么算超时

升级本身要多久事先规定不了：眼镜主控走 BLE，实测一轮 550~780 秒，换机器、换包大小都会变。所以**不设「总共不能超过多少秒」**，只看有没有进展。

下列三路信号，任一路在变就说明还在升级，就继续等：

1. 页面上的升级百分比变了。
2. 页面文案或界面本身变了。
3. 固件数据还在传。眼镜看 `X-LOG` 里的两个单调指标：`ota progress ... progress=76.7` 的数值、`offset : 1054240` 的写入偏移，只升不降。手表链路读不到这些，就看页面百分比。

三路都连续 `upgrade_stall_timeout` 秒（默认 300 秒）没有变化，才判「卡住」并记 `FAIL_UPGRADE`，备注会写明已经多少秒没有进展。

判定里有几处细节，都是为了不误杀正常升级：

- 传输水位线只升不降。眼镜重传分片时 `progress` 会往回跳（实测见过 77.34→76.93），如果跟着降，等它爬回 77.19 就会被当成新进展，卡住的传输也能一直续命。
- 不按日志行数判断。滚动窗口里条数会抖，一抖就当成没进展，等于换个方式误判。

> 2026-11-10 之前用的是 `upgrade_total_timeout: 600` 固定总超时。实测正常升级要 595~780 秒，贴着上限，正常升级也会被判成超时失败。真机链路（手表、眼镜）已经不用这个参数了。
>
> 注意 `config/global.yaml` 里仍然保留着 `upgrade_total_timeout`，那是给 `server/engine/state_machine.py` 用的。该状态机目前只在 `--dry-run` 上跑。手表、眼镜、戒指的真机执行都不走它。改它不会影响真机判定。

## 改完代码要重启服务

`python start.py` 起的服务把模块加载在内存里，**改完 `server/` 下的代码不会自动生效**。不重启的话，新任务跑的还是旧逻辑。

2026-11-10 晚就踩过这个：18:10 改完代码，但服务是 16:36 起的，19:23 跑的全量任务用的还是旧代码，T08 因此在 600 秒处被硬切，日志里写着早就删掉的「超过升级总超时」。

改完代码后按一次 `Ctrl+C` 再 `python start.py`。判断有没有跑旧代码：看日志里的报错文案在不在当前源码里。

## 息屏之后屏幕不亮

T08 会真的把屏幕关掉。这台 OPPO 上 `settings put global stay_on_while_plugged_in` 会被 `WRITE_SECURE_SETTINGS` 挡住（实测一直 `SecurityException`），所以工具不再依赖它，只用 `input keyevent 223` 关、`224` 开。

如果上一次任务异常退出，屏幕可能停在熄灭状态。新代码在每次判定页面前会先检查屏幕，灭着就点亮并提示「屏幕是灭的，先点亮再判断」。

屏幕灭着时 uiautomator 只能抓到一份没有 App 文案的空页面，任何页面判断都会失真——2026-11-11 早上的验证就撞到过一次，开场直接报「上一轮升级未结束」，实际是黑屏。手动恢复：`adb shell input keyevent 224`。

### 黑屏会把升级误判成失败（2026-11-12 已修）

手表链路原来**没有**这道保护（眼镜有），T08 因此吃过亏：息屏注入后 `_phase()` 读到空页面，既不认为在升级、也找不到按钮，直接报 `FAIL_UPGRADE`。

当时日志是铁证：

| 现象 | 说明 |
| --- | --- |
| `Could not detect idle state` × 105 | uiautomator 等不到页面空闲 |
| `Node not found` × 68 | `tv_upgrade_percent`、`tv_upgrade_state` 全读不到 |
| 同一秒 `BleLog: onCharacteristicWrite` / `writeCompleted: true` | **固件正在正常写** |

升级根本没失败，是工具瞎了。现在 `_phase()` 判断前会先确认屏幕亮着（`_ensure_screen_on`），灭的就点亮再判。

> 这道保护只在**判断页面时**生效。T08 注入息屏的 11 秒里 `_wait` 循环停摆，用例要测的息屏窗口不会被提前点亮，测试意图不受影响。

### T08 息屏失败 = 产品问题（验收不过）

T08 要求息屏后升级仍能成功。工具只如实记结果：**失败就记 `FAIL_UPGRADE`，算发现问题，不能当「可接受」放过。**

2026-11-13 在 Ultima Flex 上对照过：全程亮屏能升完；升到约 20% 息屏几秒就会「固件升级失败」。那是手表/固件侧缺陷，不是工具误判。验收时 T08 必须 PASS；若 FAIL，提给设备侧修息屏保持连接，而不是改工具放水。

> 报告备注把原因写最前面，例如「失败：固件升级失败（…）」，避免读成导航问题。

### 收尾读不到设备页（2026-11-13 已修）

DaFit 2.9.23 首页 tab 也有状态栏文字「蓝牙已连接」。原来的 `_on_device_page()` 用连接文案兜底，被状态栏骗过，以为已经在设备页，于是不切 tab，接着读不到连接控件，最后判成「升级成功，但没有回到设备页确认连接」——一次 100% 成功的升级被记成 `FAIL_UPGRADE`。

修法：`_on_device_page()` 只认 App 自己的控件或设备名；`_connect_text()` 的兜底查询限定包名；万一还是切不过去，重启一次 App 再试，仍不行才返回 `unseen`。

## 失败自动重试（会留痕）

单条用例失败后会自动重拉，默认 `case_retry_times: 2`（即最多跑 2 次）。

只重试**可恢复**的失败：

| 结果码 | 是否重试 | 原因 |
| --- | --- | --- |
| FAIL_UPGRADE | 重试 | 手表 DFU 偶发自己断，重新点升级通常能过 |
| ERROR | 重试 | 单轮代码异常，多半是页面还没到位 |
| ABORT_ENV | **不重试** | 没包、电量不足、App 没登录，重试还是同一个结果 |
| HUNG_DEVICE | **不重试** | 设备真失联，该立刻停下来看现场 |

**重试通过不会记成干净的 PASS。** 报告里「尝试」列会写清楚，比如：

```
1.FAIL_UPGRADE → 2.PASS
```

备注会写「第 2 次尝试才通过（前 1 次失败）」，HTML 里这条的备注是**黄色底**。

看到黄色就要警觉：这条用例在这台设备上不稳定，别当成一次干净通过。

### 写过固件之后不再自动重刷

这条限制比重试优先级更高，三条链路都生效。

只要这一轮**真的开始往设备里写固件**了（戒指看 `onProgressChanged` 或 `onBootLoaderState：true`，手表/眼镜看点过升级），失败后就**不再自动重刷第二遍**，备注会写「本轮已经写过固件，为避免刷死设备，不再自动重刷」。

> 2026-11-12 的教训：一台 Da Ring S4 升级反复在 5% 掉线，工具按 `FAIL_UPGRADE` 自动重拉，App 又从 0% 重传，几轮之后戒指停在 bootloader、直接开不了机。
>
> 写入中断过的固件再整包重刷，是最容易把设备刷死的操作。宁可停下来让人看现场，也不要自动再来一遍。页面都没进去（没写任何数据）的失败仍然会自动重试。

### T04/T05 这类「故意打断再重试」的用例不受上面两条限制

T04（杀 APP）、T05（关蓝牙）本来就是**要让这一次失败、然后重新点升级成功**。上面两道防线（禁止重刷、反复回 0% 判失败）不会误伤它们，原因是：

- 判据只统计**本次升级开始之后**的日志（按 logcat 时间戳切），上一次被打断的 0% 和 DFU 报错不会被算进重试那一次。
- 「禁止自动重刷」管的是**同一条用例整包重来**，用例内部的「重新点升级」是正 proceed 设计的一部分，照常执行。
- 每次重新点升级都会重设时间基准，重试阶段从新的 0% 开始计数，不会一进去就判卡死。

这三条都有单测锁定（`NoRewriteAfterFirmwareWriteTest`、`RingResumeGuardTest`），改动重试逻辑时先跑一遍。

## 单条异常不会终止整个任务

以前一条用例代码异常就把整场全量打成 `ERROR` 停掉。现在改成：

- 单条异常记 `ERROR`，**继续跑下一条**
- 连续 `max_consecutive_error` 条（默认 2）都异常，才终止任务

这样一次偶发崩溃不会毁掉后面几十分钟的测试。

## 用例之间的间隔

相邻两条用例之间默认停 `case_gap_seconds` 秒（当前 `config/global.yaml` 为 20 秒），第一条不等。

原因：手表连续升级时，偶尔来不及准备下一次握手。上一轮刚结束就点升级，会直接弹「固件升级失败」，有时甚至在 0% 就失败。2026-11-11 手表全量里 T04/T05/T08 就是这样挂的，而同样的 T04 单独跑完全正常（10.5 分钟跑完 0%→100%）。

8 条用例总共多花约 3.5 分钟。嫌慢可以调小，但不能低于手表实际恢复需要的时间。

## 升级页显示「已是最新版本」

后台明明配了包，但 App 停在「已是最新版本」，这是最常见的一种卡壳。工具的顺序是：

1. 先按页面判成「没有可升级的包」，杀一次 App 重新进入再看一遍。
2. 重启后还是「已是最新版本」，就记 `ABORT_ENV` 并终止任务，日志会写明去后台换包。

如果只是页面没刷新，重启这一步就能救回来，任务会继续正常跑。

眼镜还会弹「请给设备充电」，提示 `只有当电池充电超过 60% 时，才能进行版本升级`。工具会点掉弹窗并记 `ABORT_ENV`，先去把眼镜充满电再开任务。


### 同版本循环：不要求版本号变化（2026-11-17）

本套 s1 用例是同版本反复刷：页面显示升级完成、能重新连上 App，就算成功。版本号可以一直不变，否则没法连续测。

三条链路在判 PASS 后只会把读到的版本写进备注（变了写「已从 A 到 B」，没变写「同版本循环，版本仍为 X」），**不会因为版本不变改成 `FAIL_UPGRADE`**。读不到版本时注明「未校验」，同样不改判。

### App 被切到后台不等于升级失败（2026-11-13 已修）

升级过程中如果把 App 切到后台（手动去连别的设备、接电话都算），页面会读不到。旧逻辑 45 秒读不到就判「升级页丢失 → 固件升级失败」。

实际上升级还在后台正常跑：实测切到后台时页面读到 69%，切回来已经到了 73%。

现在会先分清两种情况：

| 情况 | 处理 |
| --- | --- |
| App 被切到后台 | 只提示「升级应该还在跑，等它回来」，**不导航、不判失败**，每 15 秒温和地拉回前台 |
| App 在前台但升级页真的没了 | 才按 45 秒超时判「升级页丢失」 |

> 关键点：后台分支**不会**按返回键、也不会重启 App。那些动作会真把升级打断，是比误判更糟的后果。

## 每条用例能不能失败

| 用例 | 这一次被打断 | 最终判定 |
| --- | --- | --- |
| T01 基线、T02 反复、T03 交替 | 不允许 | 升级成功且设备页已连接 |
| T04 升级中杀 APP | 允许失败 | 重新点升级必须成功 |
| T05 升级中关蓝牙 | 允许失败 | 蓝牙恢复后重新点升级必须成功 |
| T06 升级中关 Wi-Fi | 手表、戒指不允许 | 固件只走蓝牙，这一次必须成功 |
| T06 升级中关 Wi-Fi | 眼镜允许 | 固件同时走蓝牙和 Wi-Fi。关 Wi-Fi 和关蓝牙一样会打断这一次，重新点升级必须成功 |
| T07 切后台、T08 息屏、T09 充电 | 不允许 | 升级成功且设备页已连接 |

需要重试的用例，干扰后没回到升级入口、或重新点升级后没成功，记 FAIL_UPGRADE。

## 干扰是否真的生效

关蓝牙、关 Wi-Fi、息屏这类动作，命令返回成功不代表系统开关真的变了。工具在每个动作后立刻回读系统开关，没变就记 SKIP 并写进日志，不会拿「升级照样成功」当通过。

部分 ColorOS/Android 11 机型上 `svc bluetooth disable` 会被权限挡掉。工具先试命令，没生效就自动打开系统蓝牙设置页，点开关控件，再回读状态确认。Wi-Fi 也有同样的兜底。换机型时如果设置页控件 id 不同，需要在 `PhoneSession._switch_widget` 里补上。

## 前置联通自检

开跑前点页面上的「蓝牙/Wi-Fi自检」。它会在这台手机上真的关开一次蓝牙和 Wi-Fi，再恢复到原来的状态，确认工具能控制这两个开关。任何一项失败就别开任务，先解决手机权限或设置页适配。

也可以直接调接口：`POST /api/env/switch_check`。

## 死机规则

探测间隔默认 5 秒，同时看 APP 文案和 `dumpsys bluetooth_manager`。

1. 第一次看到未连接，记下 t0。
2. t0 之后 120 秒内重连，视为正常重启。
3. 180 秒仍未连接，再连续 3 次探测都是未连接，才记死机。
4. 确认前会检查手机还在、蓝牙开着、APP 进程还在、没有飞行模式、屏幕没有锁住。任一不满足，记 ABORT_ENV，不算设备死机。
5. 整轮都没有断开时，不因为「没断过」判失败，改由版本和成功文案下结论。

## 临时目录

截图缓存、日志缓存、界面 dump 都在 `runtime/`。页面上的「清空临时目录」会删掉这个目录再自动重建。`output/` 里的报告和归档日志不会动。

## 速度

界面判定原来每轮要读十几次前台包名、好几十次控件存在性，每读一次都是一次 JSON-RPC 或 adb 往返。实测优化前后：

| 操作 | 优化前 | 优化后 |
| --- | --- | --- |
| 一次页面判定 `_phase()` | 4.4 秒 | 0.13 秒 |
| 一次连接状态判定 `_read_link_state()` | 44 秒 | 14 秒 |
| 进入升级页前的准备 | 36 秒 | 7~9 秒 |
| 每轮轮询里收起通知栏 | 每 2 秒一次 adb | 每 4 秒一次 |

做法是一份界面快照在 `ui_cache_ttl` 秒内复用，并在点击、返回、切前后台、滚动后显式失效。升级传输本身的时间省不掉，省的是判定和导航。

如果换了机型发现判定读到旧页面，把 `config/global.yaml` 的 `ui_cache_ttl` 调小，或设成 0 完全实时。


## 不覆盖的场景

重启穿戴设备、把设备拿远断开蓝牙、多次拔插充电线、升级过程中途插入充电线。这些需要物理操作，页面和报告里都没有对应列。

## 常见问题

- 启动即提示占位包名：还没做元素校准。
- 提示需要一台手机：`adb devices` 不是恰好一台 `device`。
- 连续出现「兜底触发」：升级页关键词没对上，按《元素校准》改 `progress_keywords`。
- 任务一开就停在 `ABORT_ENV`：看备注。写着「已是最新版本」就去 PHP 后台换包；写着电量不足就把眼镜充满。
- 报告里 githash 为空：链路 yaml 的 `githash_field` 还没指到真实控件，可以在页面手填，报告会标成人工填写。
